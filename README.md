# count_tools

基于「统计工具」的个人客制化项目，计划面向中国本土地下偶像爱好者，提供 **Cheki（拍立得合影）记录与特典券管理**。

希望解决的日常问题是：拍过多少张、哪些还没领取、手里有哪些券，以及每次拍切实际用了什么券。多人合影的实际张数与成员参与数分开统计，券库存与历史成本可以追溯。

## 当前状态

**M2 核心 MVP 已交付 S25 试用，待用户功能验收。** 最新本地永久签名候选为 **1.0.0-rc.5 / 13022**，手机仍为 **rc.4 / 13021**；此前已完成用户指定旧快照的携带，尚未正式发布。取色器增加预设、HEX 与 RGB 输入；新候选补齐旧颜色兼容继承、团体标签刷新、记录合并显示和首页发生日期倒序，Android升级及交互尚未验收。后续开发继续按规划在本地推进。采用 Flutter / Dart / SQLite，固定 Flutter 3.47.5，独立应用名「Cheki账本」及专属签名。M0、M1与M2的证据分别保留，安装与数据核对不代表阶段验收通过。

首页、记录和券库已接实际数据库，采用浅蓝浅粉的极简布局。可管理团体、成员、同人关联和尺寸，保留颜色、改名、转团及身份历史。记录发生日期只到天，录入/修改动作另留时间；无签、有签、宿题互斥，背签仅有签可用；已领、部分领取、未领分开，可全字段编辑和逐批补领。原通用记录从「管理 → 旧版项目」进入。

所有业务条目信息可留空，先保存已知事实、以后补齐。历史与编辑不套新建默认，不猜测今天、零张、未领取或成本；原ID、录入时间、缺键、NULL、原文和未知字段保留。只有实际库存动作才要求明确该动作所需的数量、日期、归属与券池。

首页最近记录按发生日期倒序。相同已知日期、成员及属性等记录可以合并显示张数，点开仍能查看和编辑原条，也可切回逐条显示；原记录及历史保留。旧成员缺失颜色从指定迁移原始资料按稳定ID继承，手动设置与显式清空优先。检查和未验项见[本地修复交付](docs/acceptance/V132_LOCAL_FIX_20261014.md)。

登记采用记录、核对两页；新录默认有签、已领取和扣券，可切仅记录或待补录。多人、多券种及各期限池扣量可独立修改，扣券明细始终展开；共同提交记录、库存和来源成本，不足或失败全部回滚。仅长期可用库存省略长期标签，没有限时库存不显示零栏；过期及历史事实保留。

券详情支持购券、送券、同/跨团及个人/通用券1:1交换。成本逐来源继承，金额原文及精确比例保留，未知成本保持未知；交换不增加购买支出或Cheki。目标按交换发生日期和操作顺序FIFO。无下游可核对修改或撤销整笔；有下游显示依赖并阻止修改，不级联重算历史。

「管理 → 备份与恢复」提供完整账本、设置和附件的导出、检查、差异预览及恢复，成功后重建页面和缓存。旧代保留，失败或中断按事务恢复。自动验证覆盖当前全模型、旧schema兼容、未知事实、完整往返及进程中断；S25 的系统文件页、指定快照恢复、完整导出读回和恢复后冷启动已检查。本次候选覆盖安装已检查，历史候选升级链、完整交互及用户功能验收仍待做。当前操作与边界见 [M2闭环交付检查](docs/acceptance/V132_HANDOFF_20261013.md)、[S25试用交付](docs/acceptance/S25_INSTALL_MIGRATION_20261013.md)及[颜色修复与暂停记录](docs/acceptance/S25_COLOR_20261014.md)。

完整 BI、结构化批量导入导出及通用旧历史迁移仍为后续计划。此次仅完成用户指定快照的独立映射与携带，没有提前交付通用批量迁移工具。已有日期分组、成员/尺寸/日期筛选、当月与待领汇总；日/周/月/年/所有的完整成员统计及每日入口尚未交付。

## 交付路线与检查点

| 阶段 | 计划交付 | 检查重点 |
| --- | --- | --- |
| M0 | 工程与数据安全基础 | 可重复构建，隔离备份恢复，失败时原库不变 |
| M1 | 记切预览 | 单人/多人数量、尺寸与状态口径正确 |
| M2 | 核心 MVP | 购券、登记扣券、状态、交换/赠送、纠错与恢复的完整闭环 |
| M3 | 完整 BI | 同一筛选下，统计、明细、图表和导出结果一致 |
| M4 | 批量数据携带与旧历史迁移 | 导入预检、重复处理、映射预览与往返校验 |
| M5 | 日用验收 | 实际升级、数据核对、交互、冷启动和恢复 |

M0、M1与M2的本地证据已交，阶段待用户复核与集中实机验收；M3–M5仍待后续实施。券库存操作、预期与实际结果见[券包检查材料](docs/acceptance/V130_HANDOFF_20261013.md)。M1 的操作步骤、预期与实际对账及未验队列见 [本地交付检查材料](docs/acceptance/M1_HANDOFF_20261013.md)。具体工作包、依赖、估算、决定和实际进度统一维护在 [MasterSheet](outputs/workflow-20261011/CountTools-MasterSheet.xlsx)。大小版本的触发条件、MVP 边界和各阶段检查示例见 [版本规划与阶段验收指导](docs/PLANNING_AND_ACCEPTANCE.md)。

## 本地开发

个人开发分支为 `personal/customization`，`baseline/upstream` 保留上游基线。默认不自动合入上游变更。

```powershell
git clone --branch personal/customization https://github.com/Seniorious66/count_tools.git
cd count_tools
git config --local core.hooksPath .githooks
python scripts/verify-mastersheet.py --baseline HEAD
```

开始业务开发前，按 [开发指导](docs/DEVELOPMENT_GUIDE.md) 建立并验证工具链。仓库提交 hooks 的配置要求见 [Git 提交追溯](docs/GIT_TRACEABILITY.md)。真实数据库、系统备份和签名保存在仓库之外；开发验证使用合成数据或隔离副本。

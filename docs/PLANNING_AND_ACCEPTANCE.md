## 为什么原来的版本表不清楚

WF-002 把 12 个开发工作包写成了 v1.1.0–v1.5.1，却没有另外定义产品发布版本、MVP 和用户检查节点。例如“v1.3.1 拍切关联扣券”增加了新能力，不能因为末位是 1 就把它解释成产品补丁。原路线是完整 V0.2 的拆解，不是已经确定的 MVP 发布计划。

WF-003 保留这些历史 ID 以维持需求和日志关联，在“版本规划”增加 O/P/Q 列和下方阶段检查表。旧范围归档，已结束 ROUND 保留；纠正含义不等于删掉原规划。

## 四层关系

| 层级 | 回答的问题 | 本项目的例子 |
| --- | --- | --- |
| REQ 需求 | 为什么要做、怎样满足需求？ | 多人实物张数与参与数分别计算 |
| 开发工作包 | 本轮实现什么、依赖什么、如何验证？ | 历史 ID v1.3.1：把 Cheki 与库存原子关联 |
| App 产品版本 | 用户升级后得到什么能力、是否兼容？ | 个人版 1.0.0：完整核心 MVP；1.1.0：完整 BI |
| M 里程碑 | 到这里能实际检查什么、何时算通过？ | M2：购券到登记、纠错、恢复的使用闭环 |

一个 ROUND 推进一个依赖已满足的工作包；多个工作包可以汇集成一个产品版本。工作包完成、候选构建、阶段验收和正式发布分别记录，不互相代替。

WF-013 起，“版本规划”按 M0–M5 连续排列：蓝色开发段 → 本段工作包 → 粉色检查表头 → 对应 M 检查点。UI-FIX-001（WF-012）单列在 M0 检查点之后、M1 开发段之前；其他流程与设计记录在后面的追溯区，不混入业务开发队列。只有这一组可编辑的 M 检查点，不另维护汇总副本。

按工作包或 M 的 ID 定位，行号会随增补变化。工作包的 O/P/Q 列仍分别是产品目标、阶段归属和拆分理由；检查点采用紧邻的专用表头，D/K/L 分别是阶段状态、实际结论和下一门槛。F 列是硬依赖，表序是建议执行顺序，不会把可以独立验证的任务变成新的硬依赖。

“M1 前”分两种问法：**进入 M1 开发段前**是 M0 的 3 个开发工作包（v1.1.0 / v1.1.1 / v1.1.2），另有已完成的 UI 修复 1 项；**到 M1 检查点为止**再加 M1 的 2 个工作包（v1.2.0 / v1.2.1），累计 5 个开发工作包 + UI 修复。历史 v 编号不是 App 发布次数；M0 是工程候选，M1 的产品目标为 0.1.0。UI 修复的原型证据已有，M1 组件与 M2 真实券库存接入仍需实施验证。

## 大小版本的触发原则

以下是个人 App 的发布编号提案（DEC-019），首次候选固定前确认。它不改变原 App 的包名、证书或版本，也不继承上游 1.0.0 的兼容承诺。

| 类型 | 触发条件 | 本项目的判断例子 |
| --- | --- | --- |
| 大版本 X | 旧流程、数据或备份存在无法由兼容层与安全迁移保持的契约断裂，或用户明确决定产品重置 | 放弃旧备份格式或改变历史解释前，先裁决影响、迁移与回退；不能用升大版为丢数据免责 |
| 小版本 Y | 兼容新增一项可以独立使用并验收的用户能力 | 在 MVP 后增加完整 BI；随后增加批量数据携带 |
| 补丁 Z | 修复已发布能力、改性能或交互，不增加能力、不改变历史含义 | 修复重复提交导致的库存错误；未发布候选的稳定化仍属同一目标版本 |
| 候选 rc.N | 同一产品目标内形成新测试候选 | 1.0.0-rc.1 → rc.2；每次候选使用新的 versionCode |

多改几个文件、增加一张表、升级依赖、高耦合、完成一个 ROUND，都不是大小版本的直接触发条件。schema 版本管理存储契约，App 版本沟通用户能力，两者独立递增。

建议个人发布序列：工程候选 → 0.1.0 记切预览 → 1.0.0 核心 MVP → 1.1.0 BI → 1.2.0 完整数据携带。M4 与 M5 都针对 1.2.0；M5 是同一版的日用验收，未发布的修复不凭空变成 1.2.1。具体产品号仍为规划目标，方向“先 MVP”已获用户选择。

首次 1.0.0 表示个人产品达到核心 MVP 的稳定交付门槛，不表示 0.1.0 数据必然不兼容；后续 1→2 才按上述兼容断裂规则判断。MVP 真正试用前仍要检查候选、安装身份、当前模型恢复及实际交互；M5 是完整 V0.2 的最终日用验收，不是让 MVP 跳过自身安全检查。

N 列原数值保留为候选 code 下界，不是承诺每工作包只构建一次。实际 code 为 `max(最新使用 code + 1, 计划下界)`；它只解决安装顺序，不能证明身份一致或功能齐全。组合验收在较新候选中进行，不降级真实安装。

## 耦合怎样影响拆分和顺序

拆包按可验证的不变量和依赖，而不是按文件数。基础机制可以单独验证；同一事务必须保持的业务变化一起提交和验收。

- 实体与迁移基础先建立；库存内核只需要实体，不必等待 Cheki 页面。
- 拍切联动同时依赖 Cheki 和库存：记录、扣券、成本分配必须同成同败；幂等和不足库存拒绝也属于这个包。
- 交换、赠送和纠错沿用同一成本链。下游已消费的购入不能单边撤销，必须先预览整个受影响链。
- 批量导入依赖成熟的业务模型，不依赖 BI 界面；两者最终在完整功能候选中汇合。
- 每个新增持久化包同时扩展备份契约，不让“先试用、以后再能完整恢复”成为默认安排。

独立迁移或紧急热修可另开工作包并记录原因；是否改变产品号仍按兼容性和用户能力判断。高耦合要求合并事务验证或收紧阶段门槛，不自动等于大版本。

## 已选定的 MVP

M2 是最早的核心安全使用闭环：管理团体/身份，按日期记录单切和多人 Cheki，保留录入/修改动作时间戳；三种领取选择及适用的补领时间，新建默认有签/已领取/扣券；购券与长期/限时库存，可靠扣券和成本分配，交换/赠送、编辑/撤销及关联纠错，查看基本总数和库存，并完整备份恢复**当时全部业务模型与设置**。初始已领取采用不设实际领取时间的允许方案，来源须与历史时间未知区分，详见 [最新登记修订](requirements/CHEKI_ENTRY_20261011.md)。

完整筛选、图表、占比和统计导出属于 M3；结构化批量导入导出、旧通用历史映射属于 M4。42 项核心需求仍保留，延期交付不等于删除。M1 只记切预览可供检查，但尚未完成券闭环，不称核心 MVP。

MVP 可以先用于新记录；携带原 App 历史需要后续映射和范围确认，不能把旧 342 条明细自动当作 342 张 Cheki。当前模型恢复门槛失败时不能宣称可安全试用；真实写入或设备安装按本轮授权执行。

## 六个阶段怎样检查

下面是 WF-003 当日快照，后续实际状态与估算看 MasterSheet。

| 阶段 | 目标产物 | 用户检查重点 | 本段 / 累计人日 |
| --- | --- | --- | --- |
| M0 | 工程与安全基础 | 重复构建、隔离备份恢复、失败原库不变 | 5–9 / 5–9 |
| M1 | 0.1.0 记切预览 | A 单切 3、B 单切 2、AB 多人 2：实物 7、参与 9；尺寸和状态分别正确 | 7–11 / 12–20 |
| M2 | 1.0.0 核心 MVP | 购券→登记扣券→状态→换/送→纠错→全当前库与设置恢复 | 12–20 / 24–40 |
| M3 | 1.1.0 完整 BI | 同一筛选下 KPI、明细、表图、CSV 对账；分母和未知金额解释清楚 | 4–6 / 28–46 |
| M4 | 1.2.0 完整功能 RC | 批量预检/重复/快照、旧映射预览、隔离往返不丢字段；汇合 BI | 7–12 / 35–58 |
| M5 | 1.2.0 日用验收 | 最新候选升级、真实数据核对、交互、冷启动、恢复及约定日用观察 | 2–4 / 37–62 |

人日是当前粗估，不是交付日期或承诺；不含用户决定、设备授权、观察等待。原 WF-002 36–60 人日历史快照保留。本轮将当前模型完整恢复前置到 MVP，交换/纠错包增加 1–2 人日，更新为 37–62。并行安排可能缩短日历时间，但不会自动消除工作量和验收门槛。

每到一个检查点交付四样东西：可操作的隔离候选/演示入口；具体操作步骤与预期值；实际前后对账和恢复/故障结果；未完成及阻塞问题。截图、测试通过或 APK 文件本身不能代替可操作结果。M0 尚无业务界面，以工程和恢复产物检查；后续阶段应从用户入口操作。

例如 M2 的验收至少包含：购入长期券 2 张×30 和 2 张×20，转出首张应继承成本 30；交换后支出和切数不增加、成本守恒；赠送只减库存。联动登记反复提交不能重复记录；故障时切、券、成本都不变；库存不足拒绝。分次领取后已领与未领之和保持总张数，领取时间不移动事件统计。最后备份并恢复到隔离副本，身份、参与、状态、库存、成本、流水、未知字段和设置逐项等价。具体跨券规则按实施前的 DEC 裁决固定，不能先编造预期。

M3 用同一合成数据验表图和导出：上述例子参与口径 A=5/9、B=4/9；实物总数仍为 7。空分母、重叠属性、期间流量与期末库存另外检查。M4 注入无效关联或重复 ID，整批拒绝后原库应不变；旧映射先看预览与差异。所有制造错误的验证都在隔离数据进行。

## 阶段状态和后续推进

阶段检查表 D 列使用“待开始、本地通过/待实机、待用户复核、已验收、需整改”；K 列记录实际结论和缺口，L 列是进入下一阶段的条件。开始检查时明确检查范围和候选，复核后将具体结果补入同一 ROUND，再同步阶段。

“已验收”必须具备所属工作包完成、前置阶段通过和真实检查证据。阶段关系校验器拒绝未完成工作包被直接标为已验收；它只检查记录一致性，不能替用户验证 App 行为。不能用完成百分比代替阶段门槛。

本地依赖满足时可继续获授权的本地开发，累计待实机风险保留；阶段安全失败时先整改。M5 需要实际设备和日用证据，观察窗口开始前约定，不照搬 SalaryFlow 的天数。安装、启动、数据核对、交互、冷启动和恢复分别记结论。

提交及个人 origin 推送按 WF-004 的用户持续授权执行，见 [提交追溯指导](GIT_TRACEABILITY.md)。通过里程碑不自动授权公开发布、真实迁移或后续全部开发。下一回合先按工作包 v1.1.0 解决身份、SDK 和有效测试基线，再实施 M0。操作入口仍见 [开发指导](DEVELOPMENT_GUIDE.md) 与 [设备流程](MOBILE.md)。

属性和扣券明细以 [WF-010 最新属性修订](requirements/CHEKI_ATTRIBUTES_20261011.md) 为准：勾选式三选一，默认有签；背签仅有签可用，切换清除禁用；扣券明细常开。真实迁移遇旧冲突组合保留原事实并预览映射。

# 数据版本与迁移指导

M0 候选使用 schema 2；当前 M1 开发源码使用 schema 3。App 产品号、工程候选号与 schema 编号分别管理。schema 2 只在旧四表旁新增 `count_tools_migrations` 版本账本，schema 3 再增加团体、尺寸、操作与修改历史，不转换旧金额、日期或记录含义。旧数据库的 schema 1/2 与工程备份格式 1 继续识别。

## 打开与失败行为

`StorageSchema` 定义存储版本、旧字段、关联与计数检查。`DatabaseHelper` 在 sqflite 的版本事务内逐级迁移，打开后再次校验；应用先等待这一过程，再显示首页和初始化设置。未来版本拒绝降级，校验失败只显示停止打开提示，绝不删库、重建或修复原历史。

迁移失败时版本、旧四表、序列、未知字段和未知表留在旧状态。迁移时不调用数据库单例递归打开，也不在版本回调内另开事务。schema 2 的账本只记迁移名称和版本，没有伪造旧记录的创建、发生或领取时间。

旧 ID 必须为正整数，已知字段按原 TEXT 契约校验，金额、类型和 ext 等可空字段保留 NULL。项目 count 必须等于子项目数量，子项目 count 必须等于明细数量，关联必须存在且同项目。未知字段按原存储类型保留，不把 BLOB 转成文字。旧日期和金额原文不因新业务要求重写。

模型内部保存原始行，展示空字符串是空值的显示方式；`toJson`、未改字段的 `copyWith` 和更新仍保留 NULL 与未知字段。相同显示值的回填不会把 NULL 改成空串。修改一个字段不能清掉其他字段；插入 ID 冲突拒绝，不用 replace 覆盖原记录。新的领域服务仍需 M1/M2 独立实现，不能沿用旧 helper 的多步写入来声称 Cheki/券原子联动已完成。

## 下一次新增持久化内容

1. 先读 MasterSheet，确定一个依赖满足的工作包并记录 ROUND。
2. 添加下一步 schema 迁移和该版本校验，保留旧迁移；同时审查模型、查询、页面、统计、缓存、完整设置和备份。
3. 工程备份检查器同步扩展版本与业务校验；完整传输全部表不代替新模型业务验证。
4. 用旧备份副本验证迁移前后字段差异、重复打开、失败事务回滚和冷启动。未知字段、ID、序列和设置须等价；只有明确的新增对象可以变化。
5. 新功能的默认值只用于新记录，不能补造旧日期、领取、成员、尺寸、成本事实。数据写入和真实设备迁移仍按本轮授权。

## schema 3：团体与尺寸

`cheki_groups` / `cheki_sizes` 保存稳定 ID、名称、停用状态、真实创建/修改动作时间和修订号。只初始化三寸/五寸定义，没有默认四寸或默认成员，不把旧子项目自动识别成团体成员。改名/停用保留原 ID 与创建动作时间，旧名称保存在修改历史中；没有硬删除入口。

`CatalogStore` 一次 SQLite 事务共同写定义、`cheki_catalog_operations` 和 `cheki_catalog_history`。同操作标识同请求返回当时结果，冲突请求拒绝；过时修订不能覆盖新内容。新增后重新读取实际 SQL 行，包含未来列的默认值；编辑保留 NULL、未知列和 BLOB。操作与历史有实际外键约束，打开/恢复时进一步核对请求、结果、历史起点、修订链和当前定义。系统动作时间回退则拒绝编辑，不伪造时间。

`catalog_storage_test.dart` 覆盖逐级升级、第二步 DDL 失败回滚、默认/自定义尺寸、改名停用及重开、幂等冲突/过时编辑、写入故障回滚、外键与审计损坏拒绝。页面检查另见 `catalog_pages_test.dart`。设置 `COUNT_TOOLS_CATALOG_ACCEPTANCE` 时，只向预先标记的仓库外新目录导出应用实际生成的合成 schema 3；随后 `test-catalog-recovery.py --source '<合成目录>'` 检查全表/序列/未知字段/设置/附件往返、冷进程读取、故障回滚及旧格式兼容。历史 M0 验收副本不能用作新 schema 的测试写入目标。

个人旧备份消费者检查是额外的本地验收，不把私人样本写入测试或 Git。仅对带 `.acceptance-copy.json` 标记的副本设置 `COUNT_TOOLS_LEGACY_ACCEPTANCE`，运行 `storage_migration_test.dart` 中的 `private isolated legacy consumers and cold bootstrap`，日志留在仓库外。必须先从只读原快照复制，测试完成后比较所有原表、字段、序列、设置和原备份，不能将源目录作为测试目标。相关历史产物见 [M0 验收报告](acceptance/M0_20261011.md)。

## 新记录输入契约（尚未持久化）

`RecordDraft` 是供记录/核对页面共享的新记录草稿，不是 SQLite 行、旧记录导入器或已实现的保存服务。发生日期严格为日历日期，张数为正整数，成员身份 ID 不重复；无签/有签/宿题互斥，背签依附有签。领取数量不能超过总张数，实际领取时间不能早于发生日期对应的上海业务日。JSON 往返和已提供的字段修改保留 NULL、未知嵌套字段及原领取时间精度；非法输入拒绝，不能靠默认值补造事实。

`ReceiptInput` 保存尚未提交的原始文本，切换状态与取消日期/时间选择保留输入。新记录默认整笔已领取且不设实际领取时间；已有实际批次或未知历史来源不会变成新的默认已领。后续实际领取批次要求明确数量和时间，历史未知时间继续留空。发生日期输入没有时间点，实际领取时间按上海时区解释并存为 UTC。

后续保存服务仍须解决成员/Person 关联规则、实体存在与停用校验、事务与操作标识、稳定记录 ID、创建/修改动作时间及审计。动作时间在实际提交时产生，不能用表单打开时间或发生日期代替。成本精度、券关联与事务属于对应后续决策及 M2；草稿不默认造成本 0 或扣券事实。真正新增记录表时须同步 schema、完整备份业务检查及冷启动恢复，当前输入往返检查不能代替数据库恢复验收。

共享输入的 `MemberOption` 仅携带稳定成员 ID、显示团体/姓名/颜色和可选标志，不是 Person 关系表或历史名称规则。搜索和改名不按文本合并身份；返回的 ID 顺序与原选择保留，停用或暂不可读取的原 ID 不静默删除。面板只管理草稿，确认没有数据库写入；保存时须用最新实体服务校验，并应用 DEC-008/014 裁决后的身份规则。颜色确认只返回表单，不把选择动作说成设置已持久化；实际存储、重开和全库恢复留待实体服务实施。

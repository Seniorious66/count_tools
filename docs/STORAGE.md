# 数据版本与迁移指导

M0 候选使用 schema 2；当前 M1 开发源码使用 schema 5。App 产品号、工程候选号与 schema 编号分别管理。schema 2 增加迁移账本，schema 3 增加团体/尺寸与审计，schema 4 增加同人/成员与审计，schema 5 允许业务字段未知并新增可空 Cheki 记录与修订。旧数据库 schema 1–4 与工程备份格式 1 继续识别，不转换旧金额、日期或记录含义。

## 打开与失败行为

`StorageSchema` 定义存储版本、旧字段、关联与计数检查。`DatabaseHelper` 在 sqflite 的版本事务内逐级迁移，打开后再次校验；应用先等待这一过程，再显示首页和初始化设置。未来版本拒绝降级，校验失败只显示停止打开提示，绝不删库、重建或修复原历史。

迁移失败时版本、旧四表、序列、未知字段和未知表留在旧状态。迁移时不调用数据库单例递归打开，也不在版本回调内另开事务。schema 2 的账本只记迁移名称和版本，没有伪造旧记录的创建、发生或领取时间。

旧 ID 必须为正整数，已知字段按原 TEXT 契约校验，金额、类型和 ext 等可空字段保留 NULL。项目 count 必须等于子项目数量，子项目 count 必须等于明细数量，关联必须存在且同项目。未知字段按原存储类型保留，不把 BLOB 转成文字。旧日期和金额原文不因新业务要求重写。

模型内部保存原始行，展示空字符串是空值的显示方式；`toJson`、未改字段的 `copyWith` 和更新仍保留 NULL 与未知字段。相同显示值的回填不会把 NULL 改成空串。修改一个字段不能清掉其他字段；插入 ID 冲突拒绝，不用 replace 覆盖原记录。新的领域服务仍需 M1/M2 独立实现，不能沿用旧 helper 的多步写入来声称 Cheki/券原子联动已完成。

## 下一次新增持久化内容

1. 先读 MasterSheet，确定一个依赖满足的工作包并记录 ROUND。
2. 添加下一步 schema 迁移和该版本校验，保留旧迁移；同时审查模型、查询、页面、统计、缓存、完整设置和备份。
3. 工程备份检查器同步扩展版本与业务校验；完整传输全部表不代替新模型业务验证。
4. 用旧备份副本验证迁移前后字段差异、重复打开、失败事务回滚和冷启动。未知字段、ID、序列和设置须等价；只有明确的新增对象可以变化。
5. 新功能的默认值只用于新记录，不能补造旧日期、领取、成员、尺寸、成本事实。数据写入和真实设备迁移仍按本轮授权。

## schema 3：团体与尺寸

`cheki_groups` / `cheki_sizes` 保存稳定 ID、名称、停用状态、真实创建/修改动作时间和修订号。只初始化三寸/五寸定义，没有默认四寸或默认成员，不把旧子项目自动识别成团体成员。改名/停用保留原 ID 与创建动作时间，旧名称保存在修改历史中；没有硬删除入口。

`CatalogStore` 一次 SQLite 事务共同写定义、`cheki_catalog_operations` 和 `cheki_catalog_history`。同操作标识同请求返回当时结果，冲突请求拒绝；过时修订不能覆盖新内容。新增后重新读取实际 SQL 行，包含未来列的默认值；编辑保留 NULL、未知列和 BLOB。操作与历史有实际外键约束，打开/恢复时进一步核对请求、结果、历史起点、修订链和当前定义。系统动作时间回退则拒绝编辑，不伪造时间。

`catalog_storage_test.dart` 覆盖逐级升级、第二步 DDL 失败回滚、默认/自定义尺寸、改名停用及重开、幂等冲突/过时编辑、写入故障回滚、外键与审计损坏拒绝。页面检查另见 `catalog_pages_test.dart`。设置 `COUNT_TOOLS_CATALOG_ACCEPTANCE` 时，只向预先标记的仓库外新目录导出应用实际生成的合成 schema 3；随后 `test-catalog-recovery.py --source '<合成目录>'` 检查全表/序列/未知字段/设置/附件往返、冷进程读取、故障回滚及旧格式兼容。历史 M0 验收副本不能用作新 schema 的测试写入目标。

个人旧备份消费者检查是额外的本地验收，不把私人样本写入测试或 Git。仅对带 `.acceptance-copy.json` 标记的副本设置 `COUNT_TOOLS_LEGACY_ACCEPTANCE`，运行 `storage_migration_test.dart` 中的 `private isolated legacy consumers and cold bootstrap`，日志留在仓库外。必须先从只读原快照复制，测试完成后比较所有原表、字段、序列、设置和原备份，不能将源目录作为测试目标。相关历史产物见 [M0 验收报告](acceptance/M0_20261011.md)。

## 新记录输入契约（尚未持久化）

`RecordDraft` 是供记录/核对页面共享的新记录草稿，不是 SQLite 行、旧记录导入器或已实现的保存服务。发生日期严格为日历日期，张数为正整数，成员身份 ID 不重复；无签/有签/宿题互斥，背签依附有签。领取数量不能超过总张数，实际领取时间不能早于发生日期对应的上海业务日。JSON 往返和已提供的字段修改保留 NULL、未知嵌套字段及原领取时间精度；非法输入拒绝，不能靠默认值补造事实。

`ReceiptInput` 保存尚未提交的原始文本，切换状态与取消日期/时间选择保留输入。新记录默认整笔已领取且不设实际领取时间；已有实际批次或未知历史来源不会变成新的默认已领。后续实际领取批次要求明确数量和时间，历史未知时间继续留空。发生日期输入没有时间点，实际领取时间按上海时区解释并存为 UTC。

后续保存服务仍须解决成员/Person 关联规则、实体存在与停用校验、事务与操作标识、稳定记录 ID、创建/修改动作时间及审计。动作时间在实际提交时产生，不能用表单打开时间或发生日期代替。成本精度、券关联与事务属于对应后续决策及 M2；草稿不默认造成本 0 或扣券事实。真正新增记录表时须同步 schema、完整备份业务检查及冷启动恢复，当前输入往返检查不能代替数据库恢复验收。

共享输入的 `MemberOption` 仅携带稳定成员 ID、显示团体/姓名/颜色和可选标志，不是 Person 关系表或历史名称规则。搜索和改名不按文本合并身份；返回的 ID 顺序与原选择保留，停用或暂不可读取的原 ID 不静默删除。面板只管理草稿，确认没有数据库写入。当前管理页通过下述实体服务实际保存；记录提交仍须在自身事务内重新校验，颜色对话框确认不等于数据库保存。

## schema 4：身份、颜色与历史

`cheki_persons` 保存用户手动建立的同人标签，`cheki_members` 用独立稳定 ID 保存团体、艺名、可空 Person 关联、RGB 颜色和停用状态。同名不产生自动关联；未知关联保持 NULL。团体归属不可在原身份上改写，转团以新身份加入新团，原身份和历史保留。为防同人重复参与，转团需先给原身份明确 Person 关联，再保持同一关联创建目标身份；原身份是否停用是独立操作。

`IdentityStore` 的事务共同写定义、操作与历史。改名、颜色、停用和关联修改保留原 ID、创建动作、NULL/未知字段/BLOB；同操作同请求重试返回原结果，过时编辑和操作标识跨服务重复拒绝。实际外键保护团体/Person/操作关联，打开或恢复时进一步校验每条请求/结果、历史连续性、转团起点、不可变字段及当前行。名字历史对应实际修改动作，不据此补造过去艺名的生效日期。

`validateSelection` 用于只读预检；记录写入必须在已有事务内调用 `selectionIn`，避免检查与提交之间变化及嵌套事务。它拒绝重复身份、同 Person 多身份、失效关联和新选停用成员/团体；修改原记录可明确保留原停用身份。引入记录表时，关联修改还须检查已有联合记录的同人冲突，不静默重写旧记录。

`verify-database.py`、完整恢复和迁移账本支持 schema 1–4。新身份真实服务的合成导出由 `COUNT_TOOLS_IDENTITY_ACCEPTANCE` 指向预先标记的新仓库外目录；`test-identity-recovery.py --source '<合成目录>'` 检查全表/序列/未知字段、完整设置和附件、再备份、新进程读取、切换故障/实际进程退出及旧格式兼容。已存在导出拒绝覆盖；不会把真实导出或旧验收副本作为写入目标。

## M1 成本引用边界

`CostReference` 只表达未分配的 NULL 或对后续分配操作的引用，不包含金额或估值。新 `RecordDraft` 默认空引用；它不是金额 0。已给定引用及未知嵌套元数据在草稿编辑/序列化中保留，非法引用拒绝。引用存在与否不证明实际分配操作存在，M2 要由业务服务和关联校验裁决。金额精度、未知成本估值、FIFO、券库存和成本计算仍按 M2 决策，旧 TEXT 金额不变。

## schema 5：空信息、实际记录与补录

DEC-045 覆盖此前“完整草稿才可保存”的规则；当前保存服务采用 `RecordInformation`，完整快捷输入仍可使用 `RecordDraft`。新建默认与旧信息补录分开；补录和编辑不会补造日期、签名、颜色、领取或数量。具体规则及后续开发检查见 [可空要求](requirements/INCOMPLETE_ENTRIES_20261012.md)。

团体/尺寸/同人/成员名称可以 NULL，成员团体和颜色也可以 NULL。迁移在原版本事务中重建四张实体定义表，仅放宽相应列；先保留全部原列和原行，子表先移除，父表先恢复，再恢复索引和触发器，复制时不重放触发器。操作与历史原样保留，未知列/BLOB/默认值不丢失；遇到无法安全处理的未知外部引用或 DDL，拒绝并回滚整个迁移，不关闭外键，不级联删除未知表数据。未知成员团体可以在原身份补齐并审计；已知归属仍不可改写，转团继续新增身份。

`cheki_records` 保存稳定 ID、原始信息 JSON、创建/修改动作时间和修订号；`cheki_record_operations`/`cheki_record_history` 共同审计实际保存，幂等重试、过时修改和故障事务保护均适用。JSON 内业务字段可以 NULL/缺键，未知嵌套字段及 `legacy_raw` 原始档案在服务补录中保留。记录信息是当前单一来源，未知信息不另写虚假汇总或参与行。M1 成本仍未接入，直接写有效成本引用拒绝，旧价格等放原始档案保留。

实际提交事务内核验已填尺寸/成员是否存在、新选停用身份和同 Person 重复参与；后续改变成员同人关联先检查当前合影，冲突拒绝。历史修订按当时成员 ID 保留，不因后续关联改变重写旧修订。打开/恢复核对全审计链、当前行、引用和三个服务的操作标识，字段为空不会绕过格式或已知数量约束。

领取批次可缺数量、来源和实际时间。已填写数量仍为正整数，已知部分之和不能超过已知总量；未知不生成领取 0 或“未领”。已明确状态但数量未知可单独保留状态提示。初始整笔已领不补造实领时刻；后续实际时间未记得可留空待补录，不用录入时刻替代。补齐实际时间仍按上海业务时区转 UTC，已存在精度/批次保持原样，发生信息只到天。

完整恢复检查支持 schema 1–5，并同步核验可空实体、记录原档、修订和未知值。`COUNT_TOOLS_NULLABLE_ACCEPTANCE` 指向新的带标记合成目录，Dart 导出当前全库；`test-nullable-recovery.py` 做跨运行时全对象/设置/附件往返、再备份、新进程读取及真实中断恢复。当前记录入口已接服务，M1 首页/筛选/日汇总和完整领取批次仍待接续，不能据此将 M1 记为通过。

## M1 记录查询与页面刷新（schema 5 不变）

`RecordStore.readModel` 在一个只读使用的事务中读取记录、团体、成员与尺寸，`RecordReadModel` 从这些行重建日汇总和筛选结果，不增加第二份日计数。总张数只需数量；日期范围再需发生日期；成员和尺寸只依赖各自已知关联。成员筛选时只计所选身份的成员张数，联合原记录仍完整列出，未选其他身份不混入该成员汇总。尺寸按稳定 ID 分开，重复记录累加但原流水不合并。同名身份不合并，停用后已有记录仍可读。

未领列表只含已明确未领/部分领，未知状态不推断；已领与待领数量需总数和已领数量均已知，否则计入缺领取数量。无日期记录不使用创建时间代替，独立分组可查。日期编辑后重新计算原/新日和月，领取时间不参与日期筛选。事务保存成功后通知所有现存记录读页面刷新，保存失败不发成功刷新；管理返回时刷新名称和颜色，冷重开仍从数据库计算。

表单只替换实际改变的字段，保留未动的缺键、NULL、空列表、空备注和未知嵌套属性；清除已知属性时也保留其未知扩展。详情显示各批数量/来源/适用时间，核对与历史显示修改前后；此批名称标签仍读当前身份目录，记录的当时名称快照和完整批次编辑是剩余 M1 范围，不称已完成。

## M1 多次领取编辑（第三批）

上段的完整批次编辑现已接入实际表单。`ReceiptEditController` 只维护尚未提交的输入，原记录及审计仍由 `RecordStore` 一次事务写入。每次领取的张数、来源和实际时间分别可空；新增批次、逐批修改或删除先在核对页看前后变化。未知的编辑缓存不是已知的零次领取，只补其他字段不写空批次或推断未领取。选未领或清空信息时原输入暂留，返回原选择可继续编辑；删除已知批次后的原信息留在修订中。

新建默认初始整笔已领不生成实际领取时间。已有初始领取可以显式补填实际时间；初始整笔来源不能与部分领/未领提示或其他批次并存。新增补领是明确的实际领取动作，时间预填为当前时刻，可修改或清空，数量不猜测。修改旧批次保留其他批次、未知元数据、缺键和原 UTC 亚秒精度；未知来源且时间已知仍合法，不补造来源。

显式的初始整笔来源本身表达已领取，因此数量未知也可保留这个已知状态；已领数量仍保持未知，不补成总数或零。没有来源或状态信息的旧条目仍显示未知，不从空缓存、录入时间或快捷默认推断。

## M1 记录名称快照（第四批，schema 5 不变）

`RecordInformation` 的可选 `member_snapshots` JSON 数组按 `member_id` 绑定参与身份，不新建第二份成员身份或数量。每项允许 `member_name`、`group_name`、`group_id`、`origin` 及逐名称来源 `member_name_origin` / `group_name_origin` 未知；其他原元数据保留。已知成员必须属于本记录且不重复，已知团体引用须存在，类型和来源须有效。Dart 与 Python 的记录、审计和恢复校验使用同一契约；没有旧行批量回填或新 DDL。

快捷新录选择成员时保存目录中真实已知的名称，来源 `entry` 明确表示录入时名称，不声称是发生日期当时的名字。补录旧信息和编辑不自动填快照。手动补齐的名称来源 `manual`；只编辑一个名称时只改变该名称来源，未改的录入时名称仍保留原来源。未知名称不存界面上的占位词，也不凭成员改名动作推断历史名生效日期。

两页表单可展开记录名称、填写或清空，核对和修订显示前后变化；取消不写库。修改日期、数量、领取、属性或备注保留未动快照、缺键、NULL 和扩展。移除成员时去掉当前记录中该成员快照，原信息留审计；保存前取消移除可恢复草稿。改名、转团新身份、停用和配置色修改都不改写已有快照。记录列表/详情/核对/历史优先快照；没有快照时当前目录仅作明确标注的参照，筛选、数量、颜色仍按稳定 ID。

`COUNT_TOOLS_NAMES_ACCEPTANCE` 可导出带标记的真实 Dart 合成数据库；`test-names-recovery.py` 检查全对象、原档、修订、名称来源、可空值、精确领取时间、设置、附件往返及中断恢复。完整 v1.2.1 仍须综合材料和最终组合签名候选；用户备份恢复页面和旧数据映射在原后续范围。

部分已知数量也不能超过已知总量，已填时间不能早于事件日期。联合记录共享同一领取列表，已领/待领不乘人数；领取信息变化不改总张数、成员张数或事件日期。新恢复检查 `test-receipt-recovery.py` 消费有标记的实际 Dart 合成库，复核多批次/可空来源/原档/全对象/设置/附件往返和中断恢复；未实现手机用户备份页面或旧库映射。第三批当时尚缺名称快照及最终 M1 组合交付；名称快照随后按第四批完成，最终组合交付仍待完成。


## 2026-10-13 库存包 schema 6

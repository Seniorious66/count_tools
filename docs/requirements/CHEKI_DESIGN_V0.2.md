## 1. 评估结论与现有差距

这是一款以 Cheki 数量、特典券库存和历史分析为核心的个人 App。业务可以用 Flutter / Dart / SQLite 实现，但属于新领域模型和主要页面的改造，不能仅给旧计数页面添加几个字段。建议沿用现有仓库、许可证和独立开发流程，逐步建立新的业务模块，同时保留旧通用计数数据的只读归档与迁移适配器。

原需求把尺寸、签名、背签、宿题、完成/领取和实际券消耗分开，业务边界合理。尤其要保留“同一 Cheki 属性可能使用不同券”“多人实物张数与参与数不同”“长期库存合并但成本不合并抹平”这三条约束。

本轮证据来自当前源码和已建立的流程/备份记录，没有连接手机或重新读取实时数据。既有导出含 342 条明细、25 个子项目、1 个项目；它是历史快照，不能直接认定为 342 张 Cheki。

| 当前源码事实 | 需求差距 | 初步处理 |
| --- | --- | --- |
| `project_data`、`sub_project_data`、`item_data` 是通用项目层级；成员层有名称和颜色 | 不存在团体、Person 和跨团成员身份 | 新建独立实体与显式关联，旧名称不自动合人 |
| `item_data` 保存日期、price/type/eventName 等文本，一条明细被计作一个记录 | 没有明确数量、多人参与、尺寸、独立属性及状态桶 | 新建数量批次与参与关系；旧记录语义另做映射 |
| `loadCost()` 直接累加 `price`，父 count 另行更新 | 无券库存、到期池、FIFO、成本继承和支出/成本区分 | 建立库存流水、成本批次及分配明细，BI 从同一来源读取 |
| 批量插入有分块事务，明细增删与父计数分开调用 | 不满足一笔拍切跨 Cheki、券和成本的原子性 | 建立统一操作服务，单事务与操作 ID 幂等 |
| DB version=1，只有 onCreate；旧 helper 使用 replace 插入策略 | 无逐级升级和关联撤销机制；覆盖写不能作为账本策略 | 先做兼容/备份基础，再引入新 schema 和关联修正 |
| 已有颜色/饼图组件及 Flutter 页面 | 可复用部分展示，不足以证明 BI 口径正确 | 先定义指标和筛选契约，再复用组件 |

## 2. 首版范围与建议边界

V0.2 的全部核心需求已列入 MasterSheet，包括团体/身份、单切/多人、状态、券种、长期/限时库存、购买与成本、联动登记、交换/赠送/修正、历史纠错、BI、批量导入导出和完整备份。不是删去库存或 BI 的极简计数版。

建议首版为 Android、本地离线、单用户，无账号和云端依赖；Flutter / SQLite 沿用仓库技术路线。这些平台/存储选择仍是 DEC-007 的建议，原需求 §16.3 尚未决定。

首版默认三寸和五寸；尺寸用定义表，预留新增尺寸。CSV 多表模板作为首个结构化导入导出格式；原文将 CSV、XLSX 作为建议格式，没有明确要求两者同时交付。XLSX 编辑导入可后续评审，不伪称已支持。完整备份独立于 CSV，必须保留所有关联、成本和流水。

不安排照片收藏、必填演出场次、任意兑换比例引擎、云同步、社交、多用户协作或通用财务记账。临期提醒先按 App 内可见信息构思；系统通知和后台定时提醒需另明确。金钱在本产品中用于券购入支出与历史成本追溯。

## 3. 页面与主要操作初稿

建议底部四个页面：**首页、记录、券库、统计**。团体/成员/券种管理、导入导出、备份和设置由页面右上角的“管理”入口进入；全局提供“拍切登记”快捷按钮。以下是信息架构草案，不是已完成的 UI 原型。

| 页面 | 首屏内容 | 主要操作与防错 |
| --- | --- | --- |
| 首页 | 本日/本月实际张数、待完成/待领取、临期券、最近操作 | 快速登记、购券；已过期和临期分开展示，不让库存总数掩盖可自动使用数 |
| 记录 | 自然日分组；成员身份与三/五寸独立汇总；联合拍摄显著标记参与人 | 展开原始操作及状态桶；按来源桶选数量改状态；进入原操作修改/撤销 |
| 券库 | 团体/个人范围筛选；每券种总量、长期量、限时量、最早到期 | 长期只显示一个合并池；限时展开截止日；购入、交换、送券、调整各独立入口 |
| 统计 | 固定筛选条、实际张数/参与数切换、KPI、表格与图表 | 日/周/月/年/全部；团体成员/Person；数量与占比、筛选明细、导出当前表 |
| 管理 | 团体、Person/成员身份、券种、尺寸、备份/导入导出、临期阈值 | 停用保留历史；跨艺名关联由用户明确选择；导入先预检与预览 |

拍切登记按以下顺序展开，常用项记忆最近选择，但不悄悄改变库存分配：

1. 业务日期 → 成员身份或多人 → 尺寸、签名/背签/宿题 → 实际张数。
2. 完成/领取数量。全部同状态时使用一个快捷选择；混合状态时展开四个数量桶。
3. 默认每位参与者一份基础券建议，允许添加附加券、换券种或选择“仅记录，不扣券”。没有明确匹配时提示选券，不自动扣其他成员或其他团体的券。
4. 每券种显示实际扣量及长期/各截止日分配。每个数值独立编辑，不自动补齐另一池；“恢复自动”是显式按钮。
5. 提交前摘要：实物张数、参与人、各券种扣量、状态、期限警示；库存不足或分配差额必须修正后提交。

例如选择券种需要 5 张，自动分为限时 4、长期 1；手改限时为 2 后长期仍为 1，界面显示“已分配 3，尚差 2”。用户可再改长期为 3，或明确改变该券种的实际消耗总量。不能为了凑齐数量暗改其他输入，也不能强制全部消耗券数等于 Cheki 张数。

多人 Cheki 的部分状态更新作用于联合记录的一部分数量。A 的成员页面和 B 的成员页面打开的是同一批联合记录；选择其中 1 张更新后，两边都显示同一状态，不分叉。

## 4. 数据模型与写入方式初稿

建议新领域使用明确关系表，旧四张业务表保留至映射完成；不要把所有新事实堆入旧 `ext` JSON。以下对象/字段是逻辑草案，具体表名和 SQL 在相应版本详细设计时冻结。

| 对象 | 核心信息/关系 | 约束 |
| --- | --- | --- |
| Group / Person | 团体；稳定的现实个人标识、展示名称 | 停用不删除历史；不按同名自动合并 |
| MemberIdentity / NameHistory | Person、Group、艺名、颜色、活动状态、名称时间段 | 转团新增身份；历史保存当时名称与团体快照，关联仍可查 |
| SizeDefinition | 尺寸 ID、显示名、启用状态 | 默认三/五寸；结构不写死尺寸 |
| Operation / RevisionLink | 唯一 ID、操作类型、业务日期、录入时间、修正关联、来源/导入批次 | 原记录可追溯；幂等键避免重复提交；取消/替代保留历史 |
| ChekiBatch | 操作、尺寸、签名维度、背签、宿题、整数数量 | 一个批次表示属性与参与集合一致的一批实际实物，不逐张建照片档案 |
| ChekiParticipant | ChekiBatch、MemberIdentity | 同成员不重复；联合记录实物数仅计算一次 |
| ChekiStateQuantity / StateMovement | 批次、完成×领取四组合的数量、转移流水 | 四桶合计=有效批次量；转移≤原桶量；各参与者共享 |
| TicketKind | 名称、团体、个人/通用、指定成员、常用 Cheki 建议、停用 | 个人/通用独立；建议关系不代替实际扣券 |
| StockPool | 券种、长期或限时、截止日 | 长期每券种一个可见池；限时按截止日分池 |
| CostLot / CostOrigin | 来源操作、来源成本、购入/目标入库顺序、数量、余量、未知成本标识 | 后台层，不作为长期券可见池；交换保留来源谱系 |
| InventoryMovement / LotAllocation | 操作、券种/池、增减量、实际成本批次分配、参与者分配关联（如适用） | 数量与成本可追溯；库存不为负；修正检查下游 |
| ImportBatch / LegacyArchive | 源格式、外部 ID、截止时点、映射与原 ID/原字段/ext | 导入幂等；旧语义未确认不可变成新事实 |

每日汇总和 BI 是读结果，不再单独写一套独立总量。可以按需建立索引或可重建缓存，但底层记录与库存/状态流水才是事实来源。缓存丢失可重建，不能借更新缓存来“修好”不一致的事实数据。

操作服务负责预检、候选分配与一次 SQLite 事务提交：Cheki 批次、参与关系、状态、库存流水、成本分配和修正关系共同成功或共同失败。操作 ID 在重复提交时返回既有结果，不重复加切扣券。数据库约束/外键、事务和服务校验共同保护数量，不能只依赖页面限制。原 helper 的 replace 策略不直接复用于新操作账目。

不必建设复杂的全量事件溯源基础设施。优先采用关系表 + 不抹除历史的操作/修正记录 + 明确分配明细；当前状态与可重建读视图保持同一事务更新。重放能力主要用于导入预检、历史校验和修正差异预览，不默认每次启动重建全库。

金额建议整数分，数量为整数；总金额与录入单价同时保留。总额不能平均四舍五入后丢掉余分，批次部分转出要稳定分摊并守恒。未知成本用明确的空值/来源标识，不能当作零成本。旧 `price` 原文和含义保留，不直接转换成券购入流水；新 schema 金额精度设计不等于重写旧金额。

成本算例：先买长期 2×¥30，再买 2×¥20，购买支出 ¥100、库存成本 ¥100。交换第一张到另一券种，源库存成本 ¥70、目标成本 ¥30，购买支出仍 ¥100、Cheki 不变。再赠送源池第一张，按 FIFO 转出成本 ¥30，源剩 2 张成本 ¥40。显示仍是每券种一个长期池，后台保留各成本来源。限时同日批次与交换后 FIFO 排序尚待 DEC-011 裁决。

## 5. 需要裁决的业务边界

这些决定已进入 MasterSheet“决策与风险”；不要求本轮全部答完，但开发相依版本前必须明确。

| 决定 | 建议默认/评审方向 | 不确定性与门槛 |
| --- | --- | --- |
| DEC-002 个人包名/显示名 | 独立个人包，与原 App 并行；显示名另确认 | 先于 v1.1.0；原签名未知，禁止卸载旧 App 解决冲突 |
| DEC-007 平台/存储 | Flutter Android + SQLite 本地；无云同步 | 原需求未定，领域契约冻结前确认 |
| DEC-008 艺名与身份历史 | 改名保留别名/时间段；转团新增身份；历史保留当时显示名 | 是否允许纠正错误 Person 关联及如何展示需详细设计，不重写原事实 |
| DEC-009 状态与多人属性 | 快捷状态可记忆/手改；正常拍切可建议已完成已领，宿题可建议未完成未领 | 建议不是强制规则；新录必须明确四桶，旧缺失状态留待映射；若参与者签绘属性不同，需决定扩展参与者属性或拆分记录的规则，不能把一张实物拆计两张 |
| DEC-010 时间与补录 | 自然日 Asia/Shanghai，周一开周，截止日当天有效；业务日期与录入时间分别存 | 补录默认只记切；追溯扣券必须按业务时点检验，不能用后来购入券补早期消耗；需明确历史与当前期限提示 |
| DEC-011 FIFO 入库顺序 | 池内稳定按入库业务日期/序号；限时同截止日也 FIFO；交换按目标入库日期排队但保留原成本 | 原文只明确长期 FIFO，不含同日限时/交换排序；回补或更正后的顺序要可预测 |
| DEC-012 成本精度/未知来源 | 总额权威、整数分，单价按总額/数量解释；原输入仍保留；修正增券可指定成本，未知明确标注 | 单价与总额冲突处理、余分归属、快照未知成本/负调整的来源确认；不隐式补价格 |
| DEC-013 历史编辑下游 | 原操作保留，生成逆向及替代操作；无下游时可一次修正 | 购入已被消耗/交换或状态已改变时，先展示后续依赖，选择逆序整体撤销/替代；用户审阅范围后原子提交，不能单边撤销或悄悄重算后续成本 |
| DEC-014 BI 去重/过滤 | 实物按批次去重；参与按成员关系；同一 Person 同一批次计一次 | 跨团多人实物按各团命中时各出现但总计去重，分组行不可相加；成员过滤后分母、Person 重复身份规则必须冻结 |
| DEC-015 导入与快照 | CSV 多表、稳定外部 ID/批次 ID；预检整批；快照与历史交易明确分模式 | 快照截止日以前交易只审计/对账，不二次增减；有引用不无声覆盖；XLSX 是否首发后追加需另定 |
| DEC-016 旧记录映射 | 原始档保留，逐类映射成员/尺寸/数量；不明确项留待映射区 | project/subproject 不等于团体/成员；price 不等于购券；不默认已领/已完成/三寸；真实迁移前刷新备份 |

BI 还要固定几个展示规则：

- 实际张数按联合记录去重，成员参与数按选中的参与关系计数，两种口径始终明确显示。
- A 单切 3、B 单切 2、AB 联合 2：实物 7，A 参与 5、B 参与 4、参与总 9；参与占比为 5/9、4/9，不以 7 当分母。
- 背签、带签等属性可能重叠，分项不一定可加成 100%；不要做误导的互斥饼图。状态四组合互斥，适合数量/比例分布。
- 空分母显示“—”，不是推测 0%。部分未知成本显示“已知金额 + 未知数量”，不能报告为完整均价；完整均价在成本完整时才给出。
- 时间筛选的购买/消耗/交换/赠送是期间流量；库存是截至选定时点的存量。当前库存另明确标注，不让“本月”筛选隐式把当前存量伪装成月末历史库存。
- 转团、改名、停用和到期不删除历史；团体/成员统计按当时成员身份归属，Person 视图只改变查询。

# 停用来源区分 fix

2026-10-20问题记录、分析及规划。下一唯一工作包 **v1.5.1-r4 / M5 / 产品1.2.0**，依赖已交付v1.5.1-r3；排在M5检查点前。预计1–2人日，拟1.2.0-rc.10、versionCode至少15014，仅规划，尚无新APK。定时任务实际PAUSED保持，须用户直接开发或明确恢复后实施。

用户要求：“已停用需要区分个人停用还是团体停用”。此处个人指具体成员身份的启用状态，不把Person同人关联标签混为成员，也不扩展为同一人的所有身份一起停用。

## 现状与原因

`identity_pages.dart`成员管理网格将`!item.active || groupMap[item.groupId]?.active == false`压成一个`inactive`布尔值。`entity_grid.dart`统一显示“已停用”，测量高度、Tooltip及读屏语义也复用这段泛化文字。因此所属团体停用时，看起来像成员自身被停用，无法判断应修改哪一项。

`member_inputs.dart`的`MemberOption.available`同样只保留最终可选性，参与成员已选标签和选择弹窗不能说明不可选来源。`identity_store.dart`的相关异常仅写“成员或团体已停用”。这是源码分析结论，不声称已在手机复现或修复。

## 目标行为

| 成员自身 | 所属团体 | 成员卡片及适用提示 |
| --- | --- | --- |
| 启用 | 启用 | 不显示停用标签 |
| 停用 | 启用 | 成员已停用 |
| 启用 | 停用 | 团体已停用 |
| 停用 | 停用 | 成员已停用、团体已停用，两种原因均可读 |

团体管理自身停用标为“团体已停用”。成员页面中的启用开关只表示成员自身状态；团体停用另作只读原因，不让成员开关看似能解除团体限制。对成员管理网格、适用编辑/核对与历史状态提示、参与成员下拉及已选摘要、相关服务异常保持相同来源解释；异常尽可能包含对应团体或成员名称。

可选性沿现有规则，显示原因与最终可选性分离；不能把“团体已停用”反写为成员active=0。团体恢复启用后，原来自己停用的成员仍停用，原来启用的成员恢复原可选性。两种原因同时存在时不得只保留其一。

成员无团体是允许的业务空信息，不等同团体停用；有非空团体ID却查不到对应实体时，沿既有关系错误/不可用提示，不编造停用原因。缺失原成员时保留“成员信息不可用/请核对原选择”，不能称个人停用。同人标签、券种自身启用及尺寸启用仍按各自实体判断，不让团体停用自动扩展到券种库存。

## 实施顺序与边界

先建立从成员和团体原始状态派生的共享原因集合或等效只读模型，再传至管理卡片、MemberOption和服务提示，最后做窄屏大字/语义和跨页回归。不复制多套判断；共享网格需接收具体状态文字或等效结构，不再只靠一个布尔值渲染所有原因。

预期文件：`lib/cheki/ui/identity_pages.dart`、`entity_grid.dart`、`member_inputs.dart`、`catalog_pages.dart`、成员选项的构造处、`lib/cheki/data/identity_store.dart`及必要只读状态组件和对应测试/UI说明。实施前再定位所有构造与校验消费者。

不改变停用业务规则、不自动停用/启用成员或券种、不改历史记录/成本/库存/颜色/稳定ID/NULL/原文/审计、不作数据库迁移。保留旧记录已选身份及原可编辑边界；不得为了显示原因增加禁止保存历史的校验。正式签名与包名沿项目固定身份。

## 验收

1. 合成目录覆盖四种状态组合，成员卡片、适用选择/已选摘要和错误提示来源一致；两种原因同时存在均显示，Tooltip/读屏能完整读取。
2. 停用和恢复团体不改成员自身active；分别自身启用/停用的成员恢复后可选性正确。团体停用不改原券种状态、库存或历史统计。
3. 历史已选停用成员、缺失成员、未填写团体及关系不可用分别保持原语义；不新造状态，不阻断原本允许的编辑。
4. 正常320–430竖屏及200%字体，3–4列管理网格的具体原因可完整读取，双原因可增高/回流而非缩字裁切；颜色不替代文字。
5. 适用widget/服务回归、静态检查、完整备份恢复兼容、生产构建/依赖审计和固定身份正式签名验签。Android/TalkBack、覆盖安装与用户验收另记，不以本地预览代替。
